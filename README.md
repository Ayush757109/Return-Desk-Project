ReturnDesk — returns desk for a small online store
Agents create and manage return / replacement requests against orders, review them, approve them with a Refund, Replacement or Store Credit resolution (or reject them), add append-only notes, and close them out. Every business rule is enforced on the server against PostgreSQL — the browser UI is a convenience, never the authority.

Deployed URL:**https://returndesk-0ji8.arcada.app/ **— live on Vercel with the Supabase PostgreSQL database attached and the seed data loaded, verified end-to-end against the production API on 27 Nov 2026 (see “Deployment status”). Stack — and one honest deviation
The assignment mandates Next.js App Router. The build environment used for this submission provides Vite + React 19 + TypeScript, Vercel serverless functions (Node.js) for the backend, and Supabase PostgreSQL — there is no Next.js runtime available in it. Rather than claiming Next.js, this implementation was built on the equivalent architecture and the deviation is documented here and in the app’s own Docs page:
Concern	Assignment	This build
Frontend	React (Next.js App Router)	React 19 + TypeScript (Vite), React Router
Backend	Next.js route handlers or Express	Node.js Vercel serverless handlers in api/ (hand-written, one file per route)
Database	PostgreSQL, must survive restart	Supabase Postgres (hosted Postgres) via @supabase/supabase-js query builder against hand-designed tables
Styling	Tailwind CSS	Tailwind CSS v4
Persistence	Relational only	PostgreSQL only — no in-memory store, JSON files, MongoDB, or browser storage
Templates	No admin/CRUD template	Built from the bare Vite starter; schema, API and errors designed below


create-next-app equivalence: if this were ported to Next.js, each file in api/ maps 1:1 to an App Router route.ts handler and each page in src/pages/ to an app/ route. The domain module (api/_lib/rules.js) and the SQL would not change.

Quick start on a clean machine
Prerequisites: Node.js 20+, a PostgreSQL database (a free Supabase project is the path used here; any Postgres 14+ reachable by Supabase/PostgREST-style access works for the SQL, see note below).
git clone <this-repo> returndesk
cd returndesk
npm install
cp .env.example .env   # then fill in the three values from your Supabase project (Settings → API)
1. Create the schema
In the Supabase SQL editor (or psql "$DATABASE_URL" -f db/migrations/001_init.sql against any Postgres), run:
db/migrations/001_init.sql

This creates return_requests and return_notes with all CHECK constraints, the partial unique index for the one-live-request rule, search indexes, and an updated_at trigger.
2. Seed demo data
node --env-file=.env scripts/seed.mjs
Expected output ends with counts like By status: { Open: 9, 'In Review': 7, Approved: 6, Rejected: 5, Completed: 6 } (33 requests, every status and every reason, notes on 20 of them). The seed deletes existing rows in the two ReturnDesk tables first — run it against a fresh database.
3. Run it
npm run build && npm run preview   # production build; /api routes need Vercel (below) or `vercel dev`
# UI-only iteration: npm run dev    # Vite dev server — pair with `vercel dev` for working /api routes
The supported way to run the full stack (UI + /api/* functions together) is Vercel:
npx vercel dev     # local full stack
npx vercel --prod  # production deploy (set the env vars in the Vercel project first)
Postgres hosting note: the API talks to Postgres through the Supabase client (@supabase/supabase-js), which issues real SQL via PostgREST against the tables above — it is a query layer over PostgreSQL, not an autogenerated BaaS CRUD surface: every route, filter, transition guard and error in api/ is hand-written. If you prefer a bare Postgres (Neon, RDS, local Docker), run the same migration and swap api/db-client.js for a pg pool; the handlers’ query-builder calls translate directly to parameterised SQL.

Data model
return_requests — id (identity PK), reference (unique, human-readable e.g. RTN-2026-K7M4QX), customer_name, customer_email, customer_phone (nullable), order_id, item_name, item_sku, quantity (1–999), reason ∈ {Damaged, Wrong Item, Size Issue, Not As Described, Changed Mind}, status ∈ {Open, In Review, Approved, Rejected, Completed}, resolution ∈ {Refund, Replacement, Store Credit} (nullable until approval), refund_amount numeric(10,2) (nullable), deleted_at (soft removal), created_at, updated_at.

return_notes — id, request_id FK → return_requests(id), author, body, created_at. Insert-only through the API; there is deliberately no update/delete path.

Decisions worth defending:
- TEXT + CHECK instead of native ENUMs for reason/status/resolution: values stay human-readable in API payloads and logs, and adding a value later is a constraint change, not an ALTER TYPE. The API validates the identical value sets (api/_lib/rules.js).
- Rule 2 lives in the schema too: resolution_matches_status (Approved/Completed must have a resolution; Open/In Review/Rejected must not) and refund_amount_coherent (Refund ⇒ amount > 0; anything else ⇒ amount IS NULL). Hand-written SQL cannot store an incoherent approval either.
- Rule 3 lives in a partial unique index (the only race-free enforcement): UNIQUE (lower(btrim(order_id)), lower(btrim(item_sku))) WHERE status IN ('Open','In Review','Approved') AND deleted_at IS NULL. Rejected/Completed/soft-deleted rows fall out of the index, which is exactly the “unless the earlier request is Rejected or Completed” clause.
- Order and customer are columns, not tables. The brief is a returns desk, not an order system; there is no orders data source to join to. Denormalising the customer contact + order id onto the request keeps the desk self-contained and matches how agents actually work (they type what the customer tells them). The trade-off (no referential integrity to a real orders table) is called out under Assumptions.
- JSON field names match column names (snake_case). One vocabulary from SQL to UI makes the contract auditable in review.
API
Method	Path	Behaviour
GET	/api/requests?q=&status=&reason=&sort=&order=&page=&page_size=	List. Search (customer name/email, order id, reference), status + reason filters, sorting (created_at, updated_at, customer_name, status) and pagination all compose in one SQL query with an exact total count. Soft-deleted rows excluded.
POST	/api/requests	Create. Server generates the reference; always starts Open. 201 with the row.
GET	/api/requests/:id	Fetch one. Soft-deleted → 404 (hidden, per Rule 5).
PATCH	/api/requests/:id	Edit customer/order/item fields. Only while Open/In Review.
DELETE	/api/requests/:id	Soft-remove (sets deleted_at). Only Open/Rejected. 200 { ok, id, reference, deleted_at }.
POST	/api/requests/:id/transition	{ to, resolution?, refund_amount?, expected_status? }. The only way to change status.
GET	/api/requests/:id/notes	All notes, oldest first.
POST	/api/requests/:id/notes	Append a note — any status. PUT/PATCH/DELETE on notes → 405 (append-only is structural, not a UI choice).
GET	/api/stats	Visible counts per status (SQL count, soft-deleted excluded).


Search input is sanitised before it reaches the ILIKE filter (PostgREST syntax characters stripped, LIKE wildcards escaped), sort fields are whitelisted, and enum filters are validated — bad query params are 400s, not silent empty lists. In the UI, search is debounced 400 ms and in-flight list requests are aborted, so typing never fires a request per keystroke.
Errors — one shape, correct status codes, never 200-for-error, never HTML
{
  "error": {
    "code": "DUPLICATE_LIVE_REQUEST",
    "message": "A live request already exists for this order and item (RTN-2026-100026, status: Open). Only one live request per order and item is allowed; the earlier request must be Rejected or Completed first.",
    "details": { "existing_id": 26, "existing_reference": "RTN-2026-100026", "existing_status": "Open" }
  }
}
HTTP	Code	When
400	VALIDATION_ERROR	Missing/malformed fields; details keyed by field name for form binding. Also: non-Refund approval carrying an amount, Refund with amount ≤ 0, invalid enum filter/sort.
404	NOT_FOUND	Unknown id or soft-deleted request.
405	METHOD_NOT_ALLOWED	Wrong verb (incl. any attempt to edit/delete a note); Allow header set.
409	DUPLICATE_LIVE_REQUEST	Rule 3 (pre-check or partial-index violation 23505 mapped here).
409	STATUS_CHANGED	Optimistic-concurrency guard tripped — someone else acted first; reload.
422	ILLEGAL_TRANSITION	Rule 1; details includes from, to, allowed.
422	RESOLUTION_REQUIRED	Approval without a resolution (Rule 2).
422	EDIT_LOCKED	Edit on Approved/Rejected/Completed (Rule 4).
422	DELETE_NOT_ALLOWED	Removal outside Open/Rejected (Rule 5).
500	INTERNAL_ERROR	Unexpected failure. Still JSON.


Why 422 vs 400: 400 means “this payload is malformed”; 422 means “well-formed, but the desk’s rules refuse it in the current state”. 409 is reserved for genuine state conflicts (duplicate live request, concurrent modification).
Concurrency
- Create/edit (Rule 3): SQL pre-check for a friendly 409, partial unique index as the hard guarantee; 23505 violations are mapped back to the same DUPLICATE_LIVE_REQUEST body.
- Transitions/edits/removals: guarded updates (… WHERE id = ? AND status = <status just read> AND deleted_at IS NULL). If no row comes back, someone else won → 409 STATUS_CHANGED. Clients may also send expected_status for an explicit early check (the UI does).
- References: generated server-side (RTN-<year>-<6 chars>, unambiguous alphabet), existence-checked with retries, backed by UNIQUE.
Business rules → where each is enforced
1. Transitions — TRANSITIONS map in api/_lib/rules.js, checked in api/requests/[id]/transition.js. PATCH cannot set status (server-managed fields are rejected), so there is no side door.
2. Approval + resolution + refund amount — transition handler + the two CHECK constraints above. Rejection clears resolution/amount; completion retains what was approved.
3. One live request per order + item — findLiveDuplicate (case-insensitive SQL on trimmed order_id + item_sku, live = Open/In Review/Approved and not soft-deleted) on create and on identity-changing edits, plus the partial unique index.
4. Edit lock — EDITABLE_STATUSES check in the PATCH handler (and the guarded WHERE status IN (...)). Notes endpoint has no status check at all — on purpose.
5. Soft removal — deleted_at timestamp; every read path filters deleted_at IS NULL; only Open/Rejected may be removed; nothing ever issues a SQL DELETE (the seed script is the sole exception, for resetting demo data).
The UI additionally only renders actions legal in the current state and mirrors validation for fast feedback, but it treats the server response as truth and displays server refusal messages verbatim (banner + toast), reloading the request after conflict errors.
Assumptions (ambiguities, decided and documented)
- “Item” identity for Rule 3 is order_id + item_sku, compared case-insensitively after trimming. SKU is required on create precisely so this rule has a stable key; item name is display text and may vary ("Boots" vs "Leather Boots") without creating a false duplicate or a false pass.
- Soft-deleted requests never block a new request for the same order + item (they are off the desk entirely; only Open/Rejected can be removed, and a removed Open request should not permanently poison that order + item).
- Quantity does not split the duplicate rule: one live request per order + item regardless of quantities (partial-quantity returns across two requests are out of scope; agents raise quantity on the single request while it is still editable).
- Refund amounts are a bare numeric displayed as USD. No currency column — a single-currency store is assumed; adding currency char(3) is a trivial migration if that changes.
- No agent authentication: the brief never asks for accounts, so note authorship is a free-text name (default “Support Agent”). This is the first gap to close for real use (see Incomplete).
- Orders/customers are free-typed reference data on the request (see Data model). Email is validated for shape, phone is optional free text.
- Extra fields on non-approval transitions are ignored (never persisted), while server-managed fields (status, reference, resolution, …) on create/edit are actively rejected — strict where state could be corrupted, lenient where it cannot.
- Malformed (non-integer) ids are 400; well-formed but absent/removed ids are 404. Page size is clamped to 1–50 rather than erroring; enum filters/sorts error instead of silently returning everything.
What is implemented
- Create requests against orders with customer identity/contact, order, item (name + SKU), quantity, reason; unique human-readable reference; optional first note at creation.
- Queue with debounced server-side search (customer/email/order/reference), status + reason filters, four sort fields × direction, pagination with exact totals — all composing in SQL; URL-synced state; per-status counts; loading skeletons, distinct empty states (no data vs no matches), error + retry; 375 px card layout alongside the desktop table.
- Detail view with full record, lifecycle stepper, chronological append-only notes timeline + composer (any status), pre-decision editing with server field errors mapped to inputs, approve flow (resolution radios + conditional refund amount), reject/complete/remove confirmations — only legal actions rendered, server refusals explained in-banner.
- All five business rules server-side (direct-API safe), consistent JSON errors with correct HTTP codes, optimistic-concurrency guards, migration + seed, .env.example, in-app Docs page mirroring this file’s key points.
Incomplete / deliberately not done (prioritised correctness over breadth)
- Next.js App Router — not available in this build environment; equivalent Vite + React + serverless-Node architecture used and disclosed above. Porting is mechanical (see the mapping note).
- Authentication / agent accounts / audit log of who transitioned what — out of the brief’s scope and the honest first item for a production follow-up. Note author is free text today.
- Partial unique index on the hosted demo database — the deployment’s database is provisioned through tooling that creates the tables but cannot execute arbitrary DDL, so on this hosted instance Rule 3 rests on the API pre-check + guarded writes. The migration in db/migrations/001_init.sql contains the exact index (and the API already maps its 23505 violations to the same 409 when applied). On any self-run setup that executes the migration — the documented clean-machine path — the hard database guarantee is in force. Relatedly, the hosted tables mirror the migration’s columns/types/FK but not every CHECK constraint; the API enforces those rules regardless.
- No un-delete UI, no email notifications, no attachments/photos, no bulk actions, no CSV export — none were required; reliable core behaviour was preferred over half-finished extras.
- Permanent automated test suite — behaviour was verified end-to-end against the live deployment with a throwaway HTTP check script (32 assertions covering every rule above: combined search/filter/pagination, duplicate 409 naming the blocking request, illegal-transition 422s, resolution/refund coherence 400s, edit-lock, delete rules, soft-delete hiding, notes append-only 405 — all passing on 27 Nov 2026; its test rows were cleaned out afterwards). That script was not kept as a maintained suite. A vitest suite around api/_lib/rules.js + handler-level tests with a disposable Postgres is the natural next step; it is not claimed here.
- GitHub publication — requires the candidate’s own GitHub account, which this build environment does not have. The workspace contains a progressive local git history ready to push (commands under Deployment status). No repository URL is fabricated.
